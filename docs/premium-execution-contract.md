# Premium Redesign Execution Contract

This contract fixes the meaning of "complete" for the 52-week premium redesign. A week is not complete only because a document exists. A week is complete only when the product, codebase, and verification artifacts prove visible movement toward a world-class UI/UX.

## Non-Negotiable Standard

The target is not a nicer hackathon app. The target is a premium product experience comparable in polish, trust, and clarity to Linear, Stripe, Vercel, Apple Wallet, Airbnb, Framer, and Notion.

Every completed week must improve at least one of these:

- first-time comprehension;
- trust and payment confidence;
- visual hierarchy and taste;
- mobile reliability;
- interaction polish;
- conversion flow;
- proof clarity;
- frontend maintainability;
- accessibility;
- perceived speed.

## Definition Of Done For Any Week

A week can be called complete only if it includes all applicable items below.

| Requirement | Meaning |
|---|---|
| Product decision | The week makes a clear decision, not a vague recommendation. |
| User-visible artifact | A screen, component, shell, copy system, flow, or demo artifact changes or is precisely specified. |
| Code or design-system artifact | The repo gains a reusable component, token, route, script, test, or implementation file when the week is implementation-scoped. |
| Acceptance criteria | The week says exactly what must be true for the work to pass. |
| Verification | There is a command, test, screenshot, or audit artifact that proves the claim. |
| Regression protection | Important decisions are covered by tests, docs, route manifests, or screenshot gates. |
| Mobile check | If the week touches UI, mobile behavior must be checked at 390px and desktop at 1440px. |
| Premium comparison | The work names the premium benchmark pattern it is trying to match or exceed. |

## Completion Labels

Use these labels honestly:

- `Strategy complete`: research, positioning, IA, and benchmark work. No claim of visual transformation.
- `Foundation complete`: tokens, components, shell architecture, QA tooling.
- `Implementation complete`: user-visible UI has changed and is verified.
- `Polish complete`: interaction states, responsiveness, accessibility, and perceived speed are verified.
- `Release complete`: full flow, screenshots, tests, and submission artifacts are green.

Weeks 1-4 are `Strategy complete`, not visual implementation complete.

## Future Week Rule

Starting week 5, I should not mark a week complete unless it includes code-level artifacts or automated quality gates. If a week is research-heavy, it must still produce a decision that constrains future implementation.

## World-Class UI/UX Score Targets

By week 52, the product should score:

| Category | Target |
|---|---:|
| First-time clarity | 9/10 |
| Visual premium quality | 9/10 |
| Trustworthiness | 9/10 |
| Mobile polish | 9/10 |
| Conversion strength | 8.5/10 |
| Interaction quality | 9/10 |
| Design-system maturity | 9/10 |
| Frontend implementation quality | 9/10 |

If any core mobile screen clips, overlaps, or hides actions, the product cannot score above 6/10 no matter how good the desktop UI looks.

## The Correct Mental Model

The year is not 52 small doc tasks. It is four escalating product transformations:

1. Strategy and design foundation.
2. Core proof flow rebuilt to premium quality.
3. Merchant, visitor, developer, and ops shells brought to product-grade depth.
4. Motion, trust, accessibility, performance, and conversion polished until the app feels inevitable.
